# Building protocols with HTTP — RFC 9205 (BCP 56)

**Text:** `../../ietf-http/reference/rfc9205.txt`
**Guide:** `../../ietf-http/SKILL.md`

## Scope

How a specification should use HTTP: resources, methods, status codes, fields, content, caching,
browser coexistence, and what must not be redefined.

**Not covered:** URI authority and query structure, which is RFC 8820 — §4.4 defers there. A draft
that trips this lens on URLs usually needs both.

**The depth already exists next door.** `ietf-http` carries RFC 9205's substance organised by topic,
plus RFC 9110, RFC 9111 and RFC 8820. What stays here is the one decision it does not make.

## Firing

The draft defines an **application** that uses HTTP: an `https` URL, a method, a status code, a
header field, a media type, or a well-known URI registration.

Each of those is something the draft *defines*. A draft that governs one of those registries rather
than registering in it — media type registration procedures, well-known URI policy — does not fire,
however often the word appears in it.

### Settle the class first

This is the whole value of the lens, and it decides whether §4 has a target at all.

RFC 9205 §1 and §2 put **generic HTTP extensions** outside most of its requirements. An application
uses HTTP to meet a specific need; a generic extension adds a capability applicable to any resource.
An httpbis draft is very often the latter, and `ietf-http` does not draw this line — its "Is HTTP
Being Used?" answers a different question.

Read §1 and §2 and decide, before applying anything else:

- **Application.** All of §4 has a target. Use the guide.
- **Generic extension.** Only §4.7 (defining a field, which routes on to RFC 9110 §16.3.2) and §4.16
  (extension mechanisms) have a target. The rest of §4 has none — and §2 still puts the full HTTP
  requirements in force, so RFC 9110 and RFC 9111 remain live even where §4 does not.

**This is not RFC 8820's classification, and the two invert.** That lens splits *Extensions* from
*Applications* under BCP 190 §1.1, defined differently. Here, generic-extension is the favourable
finding — most of §4 loses its target. There, Extension is the unfavourable one — §2.4's query
prohibition becomes unconditional. Settle each lens's class separately and do not carry one across.

### Versus only looking like it

A generic HTTP extension is not an application. The fire test above catches every one of them, so
the class decision is the only thing standing between this lens and findings against requirements
RFC 9205 disclaims. Get it wrong in the permissive direction and the findings look well-grounded —
they cite real sections — and are worthless.

The most common finding is silence rather than error: a draft specifies a request and says nothing
about the response. Silence still needs quoting — quote the one sentence that does describe the
response, and show the search that found nothing else.

Do not raise a well-known URI *path* prefix as a problem: §4.4.1 explicitly sanctions putting an
application's resources under one, and RFC 8820 §2.3 names it as the exception.

`ietf-http` is written for an author changing the document; you are judging one. Its recommendations
are mostly advisory by design, and it says so. A finding needs the RFC's words, not the guide's —
quote from `../../ietf-http/reference/rfc9205.txt`, and use the guide to reach the right passage.

## What this lens asks

- Does the document say what the response *is* — status codes, media type, freshness — or only what
  the request looks like?
- What does a client conclude from each class of failure, and is "not found" distinguishable from
  "could not ask"?
- Are new formats given registered media types, or served as `application/octet-stream`?
- Is anything generic to HTTP being re-specified here?
- Are the resources reachable by a browser, and does the document account for that?

## Where to look

`ietf-http` is organised by what the draft does. Go to the headings that match:

| The draft… | `ietf-http` heading |
| --- | --- |
| defines a header or trailer field | *Header and Trailer Fields* › *Defining New Fields*; *Editorial Style* › *Structured Fields* |
| defines or uses status codes | *Status Codes*; *Resources and URIs* › *Redirection* |
| defines or uses methods | *Methods* |
| defines URL structure or discovery | *Resources and URIs* (and the RFC 8820 lens) |
| defines a format | *Content* |
| says anything about caching, or nothing | *Caching* |
| is reachable by a browser | *Web Compatibility* |
| constrains how HTTP is implemented | *Anti-Patterns* |
| shows examples, or none | *Editorial Style* › *Example Messages* |

*Anti-Patterns* › *Subsuming Generic Semantics* is the one to read even when nothing obviously
points at it: it carries §4's central prohibition on redefining generic protocol elements, and the
worked example of an over-constrained response.

## Without `ietf-http`

If the skill is not installed the text is not there either -- fetch RFC 9205 from the RFC Editor
and walk §4 after settling the class, guided by the questions above. Expect it to cost several
times as long, and say in *Could not obtain* that the HTTP guide was unavailable.
