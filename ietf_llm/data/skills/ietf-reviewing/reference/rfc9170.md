# Extension viability -- RFC 9170

**Text:** `rfc9170.txt`

## Scope

Whether an extension point will still work the first time someone needs it. The claim is empirical,
not aesthetic: a mechanism stays available only because it is used, and one that sits idle rusts
shut.

**Not covered:** whether the extension point is well designed or properly registered -- that is
RFC 6709. This lens assumes the point exists and asks what happens when it is finally exercised.

An IAB document, informational. It carries no requirements; a finding cites it for the argument, not
for a violation.

## Firing

The draft defines *or registers into* an extension point: a version field, a reserved value, a
registry, a dictionary key, a negotiation mechanism, an unknown-element rule.

### Versus only looking like it

**This lens produces supporting results as often as concerns.** §3.4 is the evidence base: HTTP
and email header fields are the RFC's own example of a point that works,
because recipients routinely ignore what they do not understand; SIP is the counter-example, where
B2BUAs that do not ignore unknown fields make new fields unreliable and slow to deploy. A draft
whose extension rides on generic HTTP field parsing is on the right side of that comparison, and
§3.4 lets you say so with a citation rather than an assertion.

§3.4 also makes a point worth quoting back at a design argument: success is often *despite* the
design, not because of it. Do not raise an inelegant extension point that is heavily exercised.

The concern shape that does hold up is a point nothing will touch until it is urgently needed --
declared in this document, used by nothing in it, with no test path anyone has run.

Before recording that a document leaves unknown-value handling unstated, check whether its base
framework already supplies the rule -- an inherited requirement restated in prose reads like an
absence and is not one.

Check whether RFC 6709 states the same thing more directly; §4.1 on under-specified versioning
usually does. Two citations on one paragraph is padding, so pick the one that tells the authors what
to change.

## What this lens asks

- Is the mechanism used by anything today, including by this document?
- If a value or version arrives that an implementation has not seen, what happens -- and has anyone
  run that path?
- Does the design add a point that nothing will exercise until it is urgently needed?
- Is there any way to detect that the point has stopped working?
- Who besides the endpoints can see, and therefore break, the extension?

## Where to look

**The argument**

- **§3** -- active use. Availability is assured only by use, and "using" means specifying,
  implementing and deploying. The section most often cited.
- **§2.2, §2.3** -- how a point falls into disuse, and how middleboxes and other third parties make
  it worse.
- **§3.1** -- depending on the mechanism beats merely offering it.
- **§3.2** -- version negotiation specifically.

**The evidence**

- **§3.4** -- worked examples: HTTP and email header fields as the case that works, SIP B2BUAs as the
  case that half-works, Diameter AVPs as a point exercised by every use of the protocol. Reach here
  to ground a claim that a point is or is not exercised.
- **§3.5** -- what restoring a broken point costs, via EDNS and its flag day. Use this when the
  authors' answer is that it can be fixed later.

**The remedies** -- where a finding needs an ask rather than an objection

- **§3.3** -- grease. Reserved values with no semantics, offered at random, so implementations meet
  unknown values routinely instead of once. The named remedy for a point nothing exercises, and the
  thing to propose before inventing one.
- **§4.1** -- fewer extension points. Sharing one point between core elements and extensions is the
  recommended pattern, so a design that does this *supports*.
- **§4.2** -- invariants. A declared invariant with a stated way to check it is good practice.
- **§4.3** -- limiting participation. Encryption and integrity protection reduce how many parties can
  break extensibility; relevant wherever §2.3's middleboxes are in play.
- **§4.4** -- feedback. Errors have to be visible or problems entrench, and §3.3's grease is only
  effective where failures are detected and reported. Pair the two: proposing grease without a way
  to see it fail is half an answer.
