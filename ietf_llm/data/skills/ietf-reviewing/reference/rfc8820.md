# URI design and ownership -- RFC 8820 (BCP 190)

**Text:** `../../ietf-http/reference/rfc8820.txt`
**Guide:** `../../ietf-http/SKILL.md` -- partial only; see *Where to look*.

## Scope

Who may define which part of a URI: authorities, paths, queries, schemes, fragments, and the
alternatives to specifying structure at all.

**Not covered:** everything else about using HTTP, which is RFC 9205. That lens's §4.4 defers the
whole URL-structure question here, so the two usually travel together.

**`ietf-http` covers about a third of this lens** -- the fixed-path rule and the remedies, under
*Resources and URIs*. It is silent on authorities, schemes, fragments and the classification below,
and on queries it states only half the rule. It is not a substitute for §2.

## Firing

The draft specifies URL structure: a fixed hostname label, a path prefix, a query parameter name, or
a rule about how a URI is constructed from something else.

### Settle the class first

**§1.1** sorts the documents this applies to into *Extensions* -- new capabilities that could apply to
any identifier or a large subset of them -- and *Applications*, which use URIs for a specific need.
Some requirements in §2 target one class, some the generic class, and which one you are reading
decides what binds. Getting it wrong produces findings against requirements that do not reach the
draft.

**This is not RFC 9205's classification, and the two invert.** That lens splits *applications* from
*generic HTTP extensions*; this one splits *Extensions* from *Applications*, defined differently.
Under RFC 9205, generic-extension is the favourable finding -- most of §4 loses its target. Under
BCP 190, Extension is the unfavourable one -- §2.4's prohibition becomes unconditional. Settle each
lens's class separately and do not carry one across.

### Versus only looking like it

The authority and the path are different questions and the answers usually differ. A registered
well-known path prefix is *fine* -- §2.3 says so, and RFC 9205 §4.4.1 encourages it. A mandated
hostname label is not. Reviews that conflate the two either miss the finding or raise a bad one.

On a deployed design, §1.1 matters as much as §2.2: the useful ask is often that the deviation be
acknowledged and its reason recorded, rather than removed. Frame it that way and the finding
survives contact with an installed base.

An origin describing its own URIs is not this document's subject. §1.1 says so directly for the
owner-allocation case, and a draft where every name in play is supplied at runtime by the party that
owns the namespace has nothing here to answer for -- however much URI structure it appears to talk
about.

## What this lens asks

- Does the document tell a domain owner what to call a host, or reach into their namespace?
- Does it constrain a path outside a registered well-known prefix?
- Does it require a query parameter that a static-file deployment cannot act on -- particularly if
  the design's own rationale is that static files should work?
- If it does deviate, does it say so?

## Where to look

- **§1.1** -- the Extension / Application split, and two carve-outs: allocation of control by a party
  that legitimately owns the URIs is not what this document is about, and existing specifications
  that already deviate are for the relevant communities to sort out. The section to read before
  asking a deployed design to change.
- **§2.2** -- URI authorities. The prohibition on specifications constraining or defining authority
  structure, with a worked example of a fixed hostname prefix. This is where a mandated
  `something.example.com` label lands. `ietf-http` says nothing about hostnames.
- **§2.3** -- URI paths, and the well-known exception that makes a registered path prefix legitimate.
  `ietf-http` › *Resources and URIs* › *Linking* carries this rule and the exception.
- **§2.4** -- queries, and the one place the class decision flips the answer outright. An
  *Application* **can** specify query syntax for resources under its control, with an operational
  caveat about deployments serving static files; an *Extension* **MUST NOT** constrain query format
  or semantics at all. `ietf-http` states only the Application half, with no class attached -- read
  §2.4 itself before using it.
- **§2.1** -- URI schemes: requiring one is fine, precluding others later is not, and defining
  substructure across schemes means modifying BCP 35.
- **§2.5** -- fragment identifiers, whose structure belongs to the media type rather than to the
  specification. Only reach for this where the draft defines fragment syntax.
- **§3** -- the alternatives, and the general position underneath the whole document: links, URI
  templates and registered well-known paths, rather than statically specified syntax. It also
  forecloses the obvious workaround -- a vendor-ish prefix on a query parameter name collides just as
  a bare name does. Where a finding needs a remedy rather than an objection, it is here, and
  `ietf-http` › *Resources and URIs* › *Linking* and *Discovery* expand on all three.
