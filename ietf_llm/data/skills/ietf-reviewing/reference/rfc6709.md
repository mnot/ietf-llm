# Protocol extensions -- RFC 6709

**Text:** `rfc6709.txt`

## Scope

Designing a protocol so it can be extended later, and extending one without breaking it. Registries,
version fields, reserved fields, unknown-element handling, and who holds change control.

IAB-stream informational, though it carries BCP 14 keywords (§1.1). A finding cites the design
consideration, not a violated requirement.

**Not covered:** whether the extension point will actually work when first used -- that is RFC 9170.
The two travel together and their findings are easy to conflate: this lens asks whether the point is
governed, RFC 9170 asks whether it is exercised.

## Firing

The draft defines or registers a version, a reserved field, an extension point, a registry, or a
rule for handling unknown elements. Registering into someone else's registry counts. So does *being*
the registry policy.

### Settle routine versus major first

§2 splits extensions by how much review they need, and the criteria are decidable.

**Major** (§2.1), if any of four hold: it modifies or extends the underlying protocol such that an
implementation of the base would need updating; it changes basic architectural assumptions, stated
or assumed by implementers; it introduces usage scenarios not originally intended or investigated;
or it changes the extension model itself, not fitting the pattern the base protocol established.

**Routine** (§2.2): none of the above, handling opaque to the protocol, no change to the base or to
deployed implementations that do not use it, and existing implementations can ignore it without ill
effect. DHCP vendor options and vendor MIME types are the worked examples.

The classification sets what the document owes. A major extension carrying routine-extension process
is a finding; a routine one held to major process is not.

### Versus only looking like it

A registry entry that is complete and a registry policy that is stated are not findings. The
findings are absences: no registry, no unknown-value rule, a version space that cannot survive
publication, a private-use convention where a registry belongs.

Check §4.2 before raising a reserved field -- the draft may already be doing the right thing, and
recording that is a result.

**Check the base protocol before recording a missing rule.** Where the draft builds on a framework
that has already answered the question, a sentence in the draft that looks descriptive may be
restating an inherited requirement. RFC 9651 §3.2 already obliges recipients to ignore unknown
Structured Fields dictionary members, so "implementations will ignore such entries" is not the draft
declining to specify -- and its absence would not have been a gap either.

## What this lens asks

- Where do new values come from after publication, and who allocates them?
- What does an implementation do with a version, keyword or field it does not recognise?
- Is this a major extension, and does the process it is getting match?
- Does anything in the identifier space depend on the document still being a draft?
- Does a reserved field say both what a sender puts there and what a receiver does with it?
- If the semantics of a code point are defined by another body, is the change-control story stated?
- Is the base protocol a critical one, and has the extension been isolated from it?

## Where to look

**The classification**

- **§2, §2.1, §2.2** -- routine versus major, with §2.1's four criteria and §2.2's test. §2 also asks
  that a protocol document say how its own extension points may be used and what review a proposal
  needs.

**The principles** -- §3

- **§3.6 Protocol Parameter Registration** -- where new values come from, and what happens when two
  extensions pick the same one. The section for "there is no registry" or "further values will be
  defined in updates to this document".
- **§3.4 "Protocol Variations"** -- design authority, quoting RFC 5704 on one body holding change
  control over code points and their semantics. The heading does not advertise it and the quote sits
  about two-thirds through; the pointer is right even though the title looks wrong. **§3.4.1
  Profiles** is the adjacent case: a restricted subset presented as conformance.
- **§3.7 Extensions to Critical Protocols** -- DNS, BGP and HTTP are named. Extending one calls for
  isolating existing uses from new ones, and the section's own lesson is that a mechanism benign
  elsewhere can still misbehave here. Reach for it on any httpbis or dnsop draft.
- **§3.2.1 Private Extensions** -- private-use and vendor-prefix conventions, and the `X-` history.
  **§3.2.2 Local Use** and **§3.2.3 Multi-Site Experiments** are the neighbouring cases.
- **§3.1 Limited Extensibility**, **§3.3 Architectural Compatibility**, **§3.5 Testability** -- the
  general design arguments, when a finding needs backing rather than a rule.

**The base protocol's own machinery** -- §4

- **§4.1 Version Numbers** -- what a specification owes about unrecognised versions.
- **§4.2 Reserved Fields** -- useful in both directions; it has cleared a draft whose
  must-be-zero-and-ignored handling was already correct.
- **§4.4 Parameter Space Design** -- whether the space is big enough and how it is partitioned, with
  a list of common mistakes starting with a version field too small to survive.
- **§4.7 Handling of Unknown Extensions** -- silent discard versus rejection, as an explicit choice.
- **§4.3 Encoding Formats**, **§4.5 Cryptographic Agility**, **§4.6 Transport** -- reach for these
  only when the draft touches them directly.
