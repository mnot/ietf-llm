# Endpoint assumptions -- RFC 3552 (BCP 72)

**Text:** `rfc3552.txt`

## Scope

What a Security Considerations section owes, and the threat model it is written against.

A **BCP**, and the only lens in this set that imposes requirements -- §5 uses MUST. A finding here
can name a violated requirement, which is not true of the informational lenses.

Those requirements bind the *authors of the document*, not the protocol. An unmet one is a
documentation defect: write "the draft does not describe X, which BCP 72 §5 requires", never "the
protocol violates BCP 72".

**Not covered:** whether the cryptography is sound, whether the chosen threat model is the right
one, or privacy as distinct from security -- that is RFC 6973.

## Firing

**Always.** Every draft has, or should have, a Security Considerations section, and this is the
document that says what belongs in one.

Calibrate on what the document is. §5's list assumes a protocol -- eavesdropping, replay,
man-in-the-middle and denial of service all need a channel and two endpoints. A data format, a
registration procedure or a process document has no such surface, and running the list against it
produces findings nobody can act on. Ask what this document's security surface actually is: for a
media type, what interpreting the content can do -- active content, external references, disclosure.

### Versus only looking like it

This lens is about the *document*, not the design. A protocol with a weak security posture that says
so clearly passes it; a strong one that leaves its assumptions implicit does not. The finding is
almost always "this is not written down", not "this is wrong".

Two consequences. It fires on every draft, so it will always return *something* -- resist padding a
review with a §5 checklist item nobody will act on. And where the concern is that a trade-off goes
the wrong way for users rather than that it is unstated, RFC 8890 carries it; this lens carries the
description.

## What this lens asks

- Does the draft say which attacks are in scope and which are out, and why?
- Does it work through the enumerated attack forms, or skip the ones that are awkward?
- Is the threat environment the global Internet across administrative boundaries, or has it quietly
  assumed a LAN or a firewall?
- Where it relies on a lower layer for security, does it say what that layer must provide *and* what
  the combined system then guarantees?
- Is there a single party whose compromise defeats the whole protocol, and is that stated?
- Is the residual risk after mitigation described, or only the mitigation?
- Are misapplications of the protocol discussed?

## Where to look

**§5 is the requirement list.** By far the most-used section; start here. It is short and almost
every clause is testable:

- **The four-part scope statement.** Authors MUST describe which attacks are out of scope *and why*,
  and which are in scope -- separating those the protocol is susceptible to from those it protects
  against.
- **The enumerated forms**, which MUST be considered: eavesdropping, replay, message insertion,
  deletion, modification, man-in-the-middle. Denial of service MUST be identified as well.
- **Cryptographic protection** -- which portions of the data are protected, with what property
  (integrity, confidentiality, endpoint authentication), what attacks the protection is susceptible
  to, and which data must be held secret.
- **Authentication assumptions** MUST be documented where the technology authenticates, with a
  worked example of the level of detail expected.
- **Lower-layer reliance.** Saying "run it over TLS" is explicitly insufficient: the protections
  that layer is expected to provide MUST be specified, and so must the properties of the combined
  system.
- **The threat environment** MUST at minimum be global-Internet deployment across administrative
  boundaries with no assumed firewalls -- even if only to justify ruling that out of scope. LAN-only
  discussion is not acceptable.
- **Residual risk** after mitigation, including risk from a compromised related protocol, incorrect
  implementation, or weakened security technology. Particular care where compromise of a *single*
  system compromises the protocol -- the RFC's own example is a certificate authority.
- **Misapplication** -- risks from foreseeable misuse, possibly with an Applicability Statement.

**The threat model** -- §3, when the draft's trust assumptions are the concern

- **§3** -- end systems are assumed uncompromised; the attacker is assumed to have nearly complete
  control of the channel, able to read any PDU and undetectably remove, change or inject packets,
  including forging traffic that appears to come from a trusted machine. Note the RFC's own point
  that "PDU" means different things per layer -- at HTTP it is a request or a response.
- **§3.1** -- limited threat models, and the passive/active split by what the attacker can do.
- **§3.2–§3.3** -- the attack catalogue: confidentiality violations, password sniffing, offline
  cryptographic attacks; replay, message insertion, deletion, modification, man-in-the-middle. Use
  it for vocabulary when naming a specific attack.
- **§3.4–§3.6** -- topology, on-path versus off-path, link-local. Reach here when the finding turns
  on where the attacker sits.

**Denial of service** -- §4.6, and it has more than the heading suggests

- **§4.6.1 Blind**, **§4.6.2 Distributed**, **§4.6.3 Avoiding** -- including the two design rules:
  make the attacker do more work than you do, and make them prove they can receive data from you.
  **§4.6.4** and **§4.6.5** work them through on TCP SYN floods and Photuris.

**The rest of §4** is a survey of mechanisms -- authentication (§4.1), generic frameworks (§4.2),
authorization versus authentication (§4.4), traffic security including IPsec and TLS (§4.5), object
versus channel security (§4.7), firewalls (§4.8). Reach for these only when the draft uses the
mechanism in question.

**§6** gives worked Security Considerations sections for SMTP and VRRP. Useful when the finding is
that a section is too thin and you want to show what adequate looks like.
