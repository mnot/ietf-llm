# Application features in the DNS — RFC 6950

**Text:** `rfc6950.txt`

## Scope

Whether a feature belongs in the DNS at all. The DNS is a loosely coherent distributed database
offering *lookup*, not search; §5 turns that into a test.

IAB-stream informational. A finding cites the misalignment, not a violated requirement.

**Not covered:** whether the DNS names chosen intrude on someone else's namespace — that is
RFC 8820.

## Firing

The draft puts data into the DNS, takes data out of it, or reads the existence of a name as a
protocol signal. Requiring an operator to publish a record — even an empty one — counts.

### Versus only looking like it

**This lens often comes back supporting the design.** §5 favours moving rich application features
out of the DNS and into application protocols, so a draft that deliberately puts key material behind
HTTPS rather than in DNS records is doing the recommended thing. Recording that is more useful to a
reviewer than most nits, because it is what stops a run of findings reading as an attack on the
approach.

Where it does fire, the finding is usually narrower than "do not use the DNS" — it is that a
*particular* use is misaligned: an identifier whose administrative model does not match the tree, or
a record inserted only to make a later lookup behave.

§5 is explicit that the DNS bootstrapping access to an application-layer protocol is a good pattern:
a NAPTR or URI record pointing at an HTTP service that fields the richer queries. A draft doing that
is not misusing the DNS, whatever else it puts in a record.

## What this lens asks

- What is being asked of the DNS, and could an application-layer mechanism carry it instead?
- Does the design require a name whose administrative owner is not the party who benefits?
- Is name existence being used as a boolean, and has the draft accounted for negative caching?
- Does an answer depend on who is asking?
- Does the data need selective disclosure, or freshness the DNS does not offer?
- Will a response fit in a UDP datagram?

## Where to look

**§5 is the test, and it is two lists.** Cite the bullet.

*Good match if all five hold:* data propagates and caches without intermediaries needing logic
beyond name, type and class; keys do not violate domain-name syntax or semantics; applications
resolve complete names rather than fragments; answers do not depend on the application-layer
identity of the asker; and the resolution ultimately serves communicating with a named service.

*Bad fit if any of these is a concern:* populating metadata about domain boundaries; names derived
from identifiers whose semantic or administrative model does not match the DNS; selective
disclosure; responses that will not fit a UDP datagram.

§5 also names the alternative — HTTP already carries structure, authentication, authorization,
confidentiality and redirection — and the boundary: HTTP should not do the DNS's job, and the DNS
should not do HTTP's, or Diameter's, or LDAP's.

**The challenges** — §3, where each §5 bullet is worked out

- **§3.1 Compound Queries**, and **§3.1.1 Responses Tailored to the Originator** — the most
  important subcase, where an administrative identity of the asker must reach the DNS. Distinguish
  it from location-specific answers keyed on source address, which §3.1.1 says are largely harmless.
- **§3.2 Using DNS as a Generic Database**, and **§3.2.1 Large Data in the DNS** — label and name
  length limits, and the pressure to fit a UDP datagram even with EDNS(0).
- **§3.3 Administrative Structures Misaligned with the DNS**, and **§3.3.1 Metadata about Tree
  Structure** — where the identifier's administrative model does not match the tree, and records
  whose only job is to predict whether a later query will succeed.
- **§3.4 Domain Redirection** — offloading redirection to the DNS, and what that costs against doing
  it at the application layer.

**The context**

- **§2.1** — service location via a record type rather than a naming convention, using MX as the
  worked example: multiple records under one name, backups, load balancing. The argument for why a
  record carries more than a name pattern.
- **§2.2, §2.3** — NAPTR and DDDS, and arbitrary data in the DNS. Reach here when the draft
  transforms a string into a name to retrieve data from TXT or a custom record.
- **§4 Private DNS and Split Horizon** — where a design assumes a globally unique answer, or
  deliberately does not. Relevant whenever the draft's guarantee depends on everyone seeing the same
  record.
